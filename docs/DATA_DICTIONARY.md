# Data Dictionary — Dynamic Organogram Manager

Field-level definitions for the core entities, matching the actual Prisma schema (`prisma/schema.prisma`) implemented in Phase 2. This supersedes the Phase 0 sketch of these entities where they differ — every difference is called out explicitly below and in `docs/DECISIONS.md`, never silently.

Conventions: every entity has `id` (UUID, PK), `createdAt`, `updatedAt` (timestamps). "Source of truth" identifies who/what owns the value. See `docs/DOMAIN_MODEL.md` for the narrative version of these rules (why, not just what) and the ER diagram.

**⚠️ Amendment to Phase 0:** Phase 0's Confirmed Decision C12 listed status values `FILLED, VACANT, PLANNED, INACTIVE`. **Deletion rule:** hard delete rejected by the database while direct reports (`primaryReportsToPositionId`) or any `PositionAssignment` reference it. **Archiving is unconditionally safe** — an archived (`INACTIVE`) position's row persists, so descendants' foreign keys remain valid and the hierarchy stays structurally intact even with an archived manager in the chain.

| positionId | UUID (FK → Position, same company) | yes      | —         | The position being filled                                                                                                           | must reference an existing, same-company position                                                                                                                | n/a    | no            | System          | `p_1`        |
| isPrimary  | boolean                            | yes      | `true`    | Reserved for future secondary/dotted-line assignments (out of MVP scope); only `isPrimary=true` rows count toward vacancy/occupancy | —                                                                                                                                                                | n/a    | no            | System          | `true`       |
| startDate  | date                               | yes      | —         | Effective start date                                                                                                                | —                                                                                                                                                                | n/a    | no            | HR              | `2023-01-01` |
| endDate    | date                               | no       | null      | Effective end date; `null` = still active/open-ended                                                                                | must not be earlier than `startDate` (DB `CHECK` constraint)                                                                                                     | n/a    | no            | HR              | `null`       |

**Concurrency-safety constraints (database-level, partial unique indexes — see `docs/adr/0009-phase2-domain-model.md`):**

- At most one row with `isPrimary=true AND endDate IS NULL` per `positionId` ("one active primary occupant per position").
- At most one row with `isPrimary=true AND endDate IS NULL` per `employeeId` ("one active primary position per employee").

**Vacancy derivation:** a Position is vacant at a given moment iff no `PositionAssignment` with `isPrimary=true` covers that moment (`startDate <= date <= endDate`, or `endDate IS NULL` for "now"). See `lib/domain/assignment.ts`'s `isVacantOnDate()`.

**Deletion rule:** never hard-deleted or overwritten — ending an assignment sets `endDate`, it never removes the row (preserves history for a future audit/reporting need).

**Retention:** generated bytes are retained until the job reaches a terminal state with no bytes to protect (`FAILED`/`CANCELLED`/`EXPIRED`), or until `expiresAt` (7 days after creation) lapses — enforced lazily on the next read that touches the job, since this app has no background job scheduler (`docs/DECISIONS.md` A41).

**Node count ceiling:** `MAX_EXPORT_NODE_COUNT` (2,500) is a defensive-only guard, currently unreachable via real data because the underlying position read is already capped at 2,000 (`docs/DECISIONS.md` A42). The reachable large-graph risk instead is a pathologically WIDE hierarchy driving the PDF tile-page count past `MAX_PDF_TILE_PAGES` (60) — rejected fast, before any page is drawn (`docs/DECISIONS.md` A43).

**Deletion rule:** never hard-deleted — a finalized job (with its bytes cleared once no longer needed) remains as an audit trail of what was exported and by whom.
