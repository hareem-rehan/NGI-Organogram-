# MVP Scope and Traceability — Dynamic Organogram Manager

Phase 13 (Release Hardening) deliverable. Maps every MVP capability named in `docs/PROJECT_SPEC.md` to the code that implements it, the phase that delivered it, its test coverage, and its current status. Every file path below was confirmed to exist (via `ls`/`find`/`grep` against the actual working tree on 2026-09-03), and every "Implemented" status was checked against real file contents, not just phase-report claims.

Status legend:

- **Implemented** — code exists, is non-trivial, and has test coverage.
- **Partial** — code exists but a named sub-requirement is missing, weakened, or not independently verified.
- **Deliberately Deferred** — explicitly excluded from MVP per `docs/PROJECT_SPEC.md` §5 / `docs/DECISIONS.md` §5, and confirmed (by grep) not to have been built anyway.
- **Not Yet Due** — scheduled for a later phase (14) that has not started; not a gap in Phase 1–13 scope.

Role-model note used throughout: `docs/PROJECT_SPEC.md` §2/§10 still describes the original four-role model (`SUPER_ADMIN`/`HR_ADMIN`/`HR_VIEWER`/`EMPLOYEE_VIEWER`). This was superseded in Phase 3 by **Confirmed Decision C14's amendment** (`docs/DECISIONS.md` §1) to a three-role model (`ADMIN`/`HR_EDITOR`/`VIEWER`), recorded in `docs/adr/0011-rbac-and-provisioning.md` and `docs/AUTHORIZATION_MATRIX.md`. A repo-wide grep confirms no `SUPER_ADMIN`/`HR_VIEWER`/`EMPLOYEE_VIEWER` string exists in `app/`, `lib/`, or `prisma/schema.prisma` outside historical docs — the three-role model is the sole implementation. ## 3. Findings for the Defect Register

**Finding 1 — "Print-friendly view" / print stylesheet named in the spec is not built, and the spec was not updated to reflect the Phase 11 team's decision to drop it.**

- `docs/PROJECT_SPEC.md` §4 lists "Print-friendly view" as its own bullet, distinct from "PDF export and PNG export" in the line above it.
- `docs/PROJECT_SPEC.md` FR-I3 reads: "Export produces PDF and PNG of the current (filtered) organogram view, **and a print-friendly stylesheet**."
- `docs/DECISIONS.md` A5 (Phase 0) documents the intended implementation: "'Print-friendly view' is a CSS print stylesheet on the existing organogram view, not a separate report generator."
- A repo-wide search for `@media print`, `print:` (Tailwind print-variant), `print-friendly`, or `printFriendly` across `app/` and `lib/` returns **zero matches**, and `app/globals.css` contains no print media query at all.
- `docs/phase-reports/PHASE_11_ORGANOGRAM_EXPORT.md` (lines 18, 25, 109, 136) confirms this was a deliberate Phase 11 decision — the team judged PDF export to "supersede" the print stylesheet for the same use case and built no separate implementation — but **neither `docs/PROJECT_SPEC.md` nor `docs/DECISIONS.md` A5 was amended** to record that scope change the way every other superseding decision in this project is (e.g. C12, C14, A4/A40 each have an explicit "AMENDED" note at the point of change). A5 today still reads as an active, unamended decision describing something that was never built.

This matters for MVP Acceptance Criterion §15.6 ("PDF/PNG export **and print view** produce a usable, correctly filtered output") — the print view half of that criterion currently has no implementation to test. Recommend either (a) building a minimal CSS print stylesheet for the organogram view as A5 originally specified, or (b) a proper, explicit decision-log amendment (matching the project's own established pattern) formally retiring the print-stylesheet requirement in favor of PDF export, with PROJECT_SPEC.md's FR-I3 and feature bullet updated to match. Leaving it as-is — an active spec requirement with silently-abandoned implementation — is the "silently assume" pattern CLAUDE.md §1.5 and §1.4 both prohibit.

**Finding 2 — Search field scope (FR-O5) narrower than the spec's literal text, without a matching decision-log amendment.**

`docs/PROJECT_SPEC.md` FR-O5 requires search to resolve "by employee name, position title, employee code, or position code." `docs/DECISIONS.md` A29 documents that Phase 9 deliberately excluded employee code from search scope (search covers position code, title, occupant display name, and department name/code only), reasoning that employee code was already excluded from the organogram's field contract as of Phase 8. This is a real, disclosed decision (unlike Finding 1) — but it is a narrower interpretation than FR-O5's plain text, and FR-O5 itself was never updated to match. Lower severity than Finding 1 because it is at least documented at the point of decision (A29), but it shares the same underlying pattern: an implementation choice that quietly diverges from an explicit Functional Requirement's wording without the requirement document itself being reconciled.

**Finding 3 — Pending Decision P1 (confidential-field visibility) is stale relative to the shipped role model.**

`docs/DECISIONS.md` P1 describes a per-field visibility flag keyed to an `EMPLOYEE_VIEWER` role that no longer exists after the Phase 3 C14 amendment (three-role model: `ADMIN`/`HR_EDITOR`/`VIEWER`). `docs/AUTHORIZATION_MATRIX.md` §4 confirms the organogram payload now excludes salary/contact/SSO/token data for **every** role by construction, which is arguably a stricter and safer outcome than P1's original per-role-flag design — but P1 itself was never marked resolved/superseded the way C12/C14/A4 were. Given MVP Acceptance Criterion §15.9 requires every Pending HR Decision to be "either confirmed... or still correctly implemented behind its documented safe default... never silently upgraded to 'final' without confirmation" — P1's documented default (a per-field flag for a role that doesn't exist) does not match what shipped, so this is exactly the kind of drift §15.9 exists to catch. Lower severity than Finding 1 (nothing is missing functionally; the actual behavior is more conservative than P1 asked for), but the decision log itself needs reconciling before MVP sign-off.

**Nothing found in this pass that indicates a functionally broken feature contradicting a phase report's "COMPLETE" claim** — every capability spot-checked against real files had genuine, non-trivial implementation and non-trivial test coverage matching its phase report's description. The three findings above are documentation/spec-reconciliation gaps (an unbuilt-but-still-specified feature, and two under-reconciled scope narrowings), not evidence of broken code.
