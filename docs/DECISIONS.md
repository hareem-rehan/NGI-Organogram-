## 0. Critical Note on the Source Proposal

[Dynamic_Organogram_Solution_Proposal.docx](source/Dynamic_Organogram_Solution_Proposal.docx) was **not present in this repository** at the start of Phase 0 (only an empty `docs/source/.gitkeep` had ever been committed). The document was located on the author's local machine (`~/Downloads/Dynamic_Organogram_Solution_Proposal_for_HR.docx`), read in full, and copied into `docs/source/` under the expected filename during this phase.

More importantly: **the document's own header states "Status: For discussion and requirements confirmation."** It is a discovery-meeting proposal, not a signed-off specification. Its Section 17 ("Meeting Notes and Agreed Actions") is a blank table — no HR decisions have actually been recorded as agreed yet. Section 14 ("Decisions Required from HR") lists open questions that, as of this writing, have no answer on file.

**Consequence:** Everything in this project that reads as a "recommendation" in the proposal is treated here as a strong, safe **default** — not as an approved requirement. Items the proposal explicitly flags as open are listed below under "Pending HR Decisions" and must not be silently finalized during implementation.

**Amendment to C12 (Phase 2):** The Phase 2 task brief explicitly instructed: _"Do not use FILLED as the only source of truth if occupancy is derived from active assignments."_ Phase 0's own data dictionary already said `FILLED`/`VACANT` should be "derived from whether an active Employee is assigned" — i.e. it already intended derivation, but stored the derived value as a literal enum member, which is exactly the anti-pattern that produces drift (the stored value can silently disagree with the real assignment data). Phase 2 corrects this, non-silently: `Position.status` is now a **lifecycle-only** enum — `PLANNED | ACTIVE | INACTIVE` — and occupancy ("filled" vs "vacant") is always **computed** from `PositionAssignment` (see `docs/DOMAIN_MODEL.md` §4), never stored on `Position` itself. This is a genuine amendment to a Confirmed Decision, not a silent change — it is recorded here, in the Phase 2 phase report, and in ADR-0009.

**Amendment to C14 (Phase 3):** The Phase 3 task brief specified a different role model — ADMIN, HR_EDITOR, VIEWER — explicitly framed as the fallback "if no final roles exist." No final HR-confirmed role list was ever recorded (Section 14 of the proposal listed the four-role sketch among its own open items, and `docs/DECISIONS.md` never elevated it past that), so the three-role fallback is now the authoritative current model. `Prisma`'s `UserRole` enum, `lib/auth/permissions.ts`, and `docs/AUTHORIZATION_MATRIX.md` all reflect it. This is a genuine amendment to a Confirmed Decision, not a silent change — recorded here, in `docs/adr/0011-rbac-and-provisioning.md`, and in the Phase 3 phase report. If HR later confirms a four-(or more-)role model, that is a new amendment to make explicitly the same way, not a reason to have kept C14 as originally written in the meantime.

These are explicitly unresolved in the proposal itself (its own Section 14 and the discovery-meeting guide in Section 15). **Do not implement a permanent, unchangeable answer to any of these.** Build the safest reversible default (see column 3) so the real answer can be swapped in later without a schema rewrite.

**Note (added Phase 13, caught by `docs/MVP_SCOPE_AND_TRACEABILITY.md`'s review):** P1/P3 below still name the original proposal's `EMPLOYEE_VIEWER`/`HR_VIEWER`/`HR_ADMIN` roles, which C14 (Phase 3) superseded with the three roles actually implemented — `VIEWER`/`HR_EDITOR`/`ADMIN`. The role names are left as originally written here (this section documents the ORIGINAL open question, not a living spec), but readers should map `EMPLOYEE_VIEWER`→`VIEWER` and `HR_VIEWER`/`HR_ADMIN`→`HR_EDITOR`/`ADMIN`. ## 5. Deferred Decisions

Explicitly out of MVP scope per proposal §6 and task brief §6. Not designed for, not stubbed, not silently half-built.

- Drag-and-drop hierarchy editing
- Secondary/dotted-line/matrix reporting
- HRMS integration and single sign-on beyond a pluggable Auth.js provider
- Future-state organization planning and version comparison
- Historical organization comparison / point-in-time views
- Advanced workforce analytics / custom leadership dashboards
- Multi-step approval workflow for structural changes
- Automatic synchronization with external systems

If a later phase seems to require one of these to function, that's a signal to stop and re-scope — not to build it quietly.
