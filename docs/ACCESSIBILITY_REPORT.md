# Accessibility Report — Dynamic Organogram Manager

Phase 13 (Release Hardening) deliverable, Step 15. Target: WCAG 2.2 Level AA. **This report does not, and cannot, claim full WCAG 2.2 AA compliance from automated testing alone** — per the Phase 13 brief's own explicit instruction. Automated tooling (axe-core) reliably catches a meaningful subset of failures (missing labels, color contrast, some ARIA misuse) but cannot evaluate meaning, task completability, or several manual-only success criteria (focus order across a full workflow, meaningful reading order, correct use of semantics beyond what ARIA rules can statically check). This report combines both: automated coverage across every named route, plus a real manual keyboard/focus spot-check, and is explicit about what neither method covers.

Rule set: `wcag2a` + `wcag2aa` tags. A test fails on any `critical`/`serious` impact violation; `moderate`/`minor` findings are not currently asserted on (see Known Limitations).

## 3. Findings

**Finding 1 (DEF-005, Medium, FIXED this phase):** the audit log table's "refreshing" row state used `opacity-60` on the whole row while a filter change was in flight, which dims text along with everything else — axe-core measured effective text contrast at 2.87:1, under WCAG 2 AA's 4.5:1 minimum (rule `wcag143`). Notably, `app/globals.css`'s `--color-muted-foreground` token was already deliberately darkened in Phase 7 specifically to comfortably pass AA at full opacity — this Phase 12 component silently undid that fix by wrapping the same token in `opacity-60`. **Fixed:** replaced with a background-only tint (`bg-muted/60`) that conveys the same "stale/refreshing" cue without touching text contrast, plus added `aria-busy` for a proper semantic signal. Verified via a full re-run of the automated check (now passing) and the full unit suite (unchanged at 988 tests / 92 files) to confirm zero regressions.

**Finding 2 (DEF-007, Low, not fixed — recommended follow-up):** closing a dialog via Escape returns focus to `<body>` instead of the triggering button. A real, reproducible manual finding, not caught by axe-core (focus-restoration-on-close is outside what automated WCAG tooling checks). Judged Low severity (a usability rough edge, not a hard WCAG failure) and left as a documented follow-up rather than guessed at under Phase 13's remaining time budget — see the Defect Register entry for the recommended fix approach (likely wiring `components/ui/dialog.tsx`'s trigger through Radix's own `Dialog.Trigger`, or adding an explicit `onCloseAutoFocus` handler).

**Nothing else found this phase.** Every other manual and automated check passed.

## 4. Known Limitations (honestly disclosed, not silently skipped)

- **Automated coverage is `critical`/`serious` impact only.** `moderate`/`minor` axe findings are not currently asserted on and were not manually triaged route-by-route this phase — a lower-priority follow-up would be to review the full (non-filtered) axe report for every route, not just the blocking-impact subset.
- **Only one browser engine was used for both automated and manual testing (Chromium).** See `docs/RELEASE_CHECKLIST.md`/the compatibility section of this phase's final report for the same Chromium-only limitation as this project's E2E suite generally (`playwright install --with-deps chromium` only). Screen-reader software itself (NVDA/JAWS/VoiceOver) was not used — this environment has no way to drive a real screen reader; the manual checks above use browser DOM/focus inspection as a proxy for what a screen reader would announce/allow, which is a real but imperfect substitute.
- **Not every dialog/interactive component was individually spot-checked for the DEF-007 pattern** — only the Departments "Add Department" dialog was manually verified; the finding is reported as "likely shared across every dialog using the same underlying component" but this was not exhaustively confirmed route-by-route.
- **Color-blindness/vision-simulation testing was not performed** — contrast ratios were checked numerically (via axe) but no simulated color-vision-deficiency pass was done across the department color-coding feature specifically (a color-only-signal risk area named in `docs/PROJECT_SPEC.md`'s accessibility requirements). Department colors are always paired with a text label/legend entry per existing design (not color-only), which mitigates but was not independently re-verified this phase.
- **No compliance certification is being claimed.** This report is evidence gathered during Phase 13; a full WCAG 2.2 AA conformance audit (ideally including real assistive-technology testing) is recommended before any external compliance claim is made.
