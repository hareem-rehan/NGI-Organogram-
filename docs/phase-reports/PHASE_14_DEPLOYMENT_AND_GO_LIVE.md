## Environment architecture

See `docs/ENVIRONMENT_MATRIX.md` for the full variable-by-variable breakdown, sourced directly from the app's own real, already-implemented Zod validation schema (`lib/env.ts`) rather than reconstructed from scratch. Two architectural facts materially simplify this phase's Steps 5/6/10/11 versus what the prompt assumes:

- **No object storage exists or is needed.** CSV uploads and generated PDF/PNG exports are stored as bytes directly in PostgreSQL for a bounded retention window (a documented Phase 10/11 decision — `docs/DECISIONS.md`). There is no bucket to provision, secure, or audit for public access.
- **No background-worker/queue infrastructure exists or is needed.** Import/export execution is synchronous within one request; expiry is lazy (enforced on next read, not a scheduled sweep). There is no worker process to deploy or monitor.

Both are pre-existing, deliberate architectural decisions from earlier phases, not gaps introduced or left open by this phase — restated here because several of Phase 14's prompted steps (5, 6, 10, 11) assume infrastructure this app's design doesn't use.

`.github/workflows/deploy.yml` (new, this phase) defines the staging→production pipeline SHAPE the prompt's Step 13 describes — pull-request checks, a release-candidate gate, a staging deploy stage, a manual-approval-gated production stage — using GitHub Environments' built-in manual-approval protection rule as the "require explicit approval" mechanism. **It is not wired to a real Vercel project or real secrets** (none exist yet — see Deployment Decisions) and has never been run; it documents the intended pipeline for when real infrastructure exists, not a working deployment path today. Vercel's own GitHub integration (once the user connects a real Vercel project to this repository) natively handles most of this — preview deployments per PR, and a production deployment on merge to `main` gated by Vercel's own project protection settings — so this workflow file's real, long-term value is documenting the manual-approval and pre/post-deployment verification gates around whatever Vercel does automatically, not replacing Vercel's own build pipeline.
