## Security Headers (Step 6) — Implementation and Regression Verification

Added `proxy.ts` (this Next.js version's renamed `middleware.ts` file convention) implementing:

- Nonce-based `Content-Security-Policy` (`script-src 'self' 'nonce-{random}' 'strict-dynamic'`, plus `'unsafe-eval'` in non-production only), with `style-src 'self' 'unsafe-inline'` kept intentionally — CSP nonces cannot apply to the inline `style={{...}}` HTML attribute (only `<style>`/`<script>` elements), and 5 existing components use it for validated, server-computed values (hex colors, percentages); rewriting them to nonced `<style>` tags is judged a UI refactor out of scope for a stabilization phase (CLAUDE.md "do not add unapproved features").
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` (defense-in-depth alongside `frame-ancestors 'none'`), `Permissions-Policy` disabling camera/microphone/geolocation/FLoC.
- `Cache-Control: private, no-store` — see finding below.
- `Strict-Transport-Security` gated to `NODE_ENV=production` only (meaningless, and misleadingly presented, over plain HTTP in dev).

**Finding (not a defect — documented framework behavior):** verified via live `fetch()` against both an authenticated RSC route (`/dashboard`) and an unauthenticated route (`/sign-in`) that the actual `Cache-Control` response header is `no-cache, must-revalidate`, not the `private, no-store` value set in `proxy.ts`. This is Next.js's own dynamic-rendering response pipeline applying its own `Cache-Control` downstream of the Proxy layer for every dynamically-rendered page — it takes precedence for this specific header on page/document responses in this Next.js version, and is outside `proxy.ts`'s control. All other headers (`Content-Security-Policy` with a fresh nonce each request, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`) were confirmed present with the exact configured values on both routes. Practical impact: `no-cache, must-revalidate` still forces any cache (browser or shared) to revalidate with the origin before serving a copy — the same practical protection against stale/shared-cache exposure of private data that `no-store` was meant to provide, just via a different (Next-owned) directive. Documented in full in `docs/SECURITY_REVIEW.md`; no code fix pursued further (would require patching Next.js internals, out of scope).

**Functional verification under the new CSP:** confirmed via the Browser pane (dev server) that client-side interactivity is unaffected — no CSP-violation console errors on `/departments` or after opening the "Add Department" dialog (a client-rendered dialog with form fields), only the pre-existing, unrelated HMR WebSocket connection failures already documented in earlier phases.

## Domain-Integrity Check (Step 9)

Built a read-only, system-wide domain-integrity checker: `lib/domain/integrity-check.ts` (18 pure, independently-computed corruption checks — see file header for the category list, derived from CLAUDE.md §2's business invariants and `.claude/skills/organogram-hierarchy-safety/SKILL.md`'s 12 hierarchy invariants), `lib/repositories/integrity-check.repository.ts` (fetches every row across ALL companies — this is a system-wide release gate, not a company-scoped feature), `lib/services/integrity-check.service.ts` (orchestration), and `scripts/check-domain-integrity.ts` (CLI entry point, `npm run check:integrity`; read-only, never repairs; exits 1 if any violation is found).

**A real, useful finding while designing the categories:** several of the 18 corruption categories are already unreachable via any Prisma write, because the schema itself blocks them — `positions_no_self_report` (CHECK constraint) and `positions_one_root_per_company` (partial unique index) prevent self-reporting and multiple roots at the database level, and the compound `[id, companyId]` foreign keys used throughout the schema (Position→Department/JobGrade/primaryReportsTo, Employee/Position→PositionAssignment, Employee→User.linkedEmployee) make most cross-company reference corruption structurally impossible. This was proven, not assumed: the new integration test suite (below) asserts the database itself rejects the first two, and confirms the compound-FK cases have no way to construct a violating row at all. The checker still implements all 18 as defense-in-depth (a future migration or direct-SQL bug could bypass these same constraints), but the two genuinely _not_ backed by any schema constraint — `AuditEvent.actor`/`AuditEvent.importJob`/`AuditEvent.exportJob`, whose foreign keys are plain (not company-compound), unlike everything else in the schema — are where this tool adds real, non-redundant coverage, alongside the case-insensitive duplicate-code checks (the DB's unique constraints are case-sensitive) and the assignment-overlap/date-range checks (stricter than the DB's own permissive `endDate >= startDate` CHECK and its open-ended-only partial unique index).

**Note on overlap with the existing Dashboard "data quality warnings" feature (Phase 7):** `lib/domain/dashboard.ts`'s `detectHierarchyIntegrityWarnings` and `lib/repositories/dashboard.repository.ts`'s `findPositionsWithMultipleEffectiveOccupants`/`findEmployeesWithMultipleEffectiveAssignments` already detect some of the same conditions, but as a single-company, UI-facing warning banner for the currently signed-in user — not a cross-company, CI-integrated, non-zero-exit release gate. Both are kept; they serve different consumers (an HR user vs. a release pipeline) and the new tool checks additional categories (audit-event/user/session consistency) the dashboard never touched.

**Tests:** 41 new unit tests (`lib/domain/integrity-check.test.ts`, pure in-memory fixtures, one positive + one negative per category plus aggregation tests) and 10 new integration tests (`tests/integration/integrity-check.integration.test.ts`, against the real test database — 2 of which assert the database itself rejects a corrupt write, the rest deliberately bypass the service layer via direct `testPrisma` calls to insert genuinely corrupt data and confirm the checker flags it). Ran `npm run check:integrity` against the test database directly: `PASS — no integrity violations found`.

## RBAC / Company-Isolation Test Matrix (Step 8)

The original Phase 13 brief asked for a matrix across "7 roles × ~13 modules." **The implemented system has only 3 roles** — `VIEWER`, `HR_EDITOR`, `ADMIN` (`prisma/schema.prisma`'s `UserRole` enum, `lib/auth/permissions.ts`) — there is no 7-role system anywhere in this codebase. Per CLAUDE.md's "do not silently assume" and "do not add unapproved features" rules, the matrix was built against the REAL 3-role model rather than inventing 4 fictional roles to hit a number from a pre-implementation planning document; this is recorded here as a documented scope clarification, not a defect.

**What was built:**

1. `tests/integration/rbac-company-isolation.integration.test.ts` (new, 26 tests). Mocks only the outermost `auth()` call (`@/lib/auth/config`, the one thing that cannot run outside a real HTTP request) and then invokes the real "use server" action functions end-to-end — real `requirePermission` → real `roleHasPermission` → real service → real repository → a real Postgres test database. This is additive to, not a duplicate of, two existing layers: `app/(app)/*/actions.test.ts` (which mock `requirePermission` itself and only assert it was _called_ with the right permission string) and the existing `*.integration.test.ts` files (which call services directly with a hand-picked `companyId`, never going through a session or the permission gate at all). Two describe blocks:
   - **"RBAC × module permission matrix"** (16 tests): for each of dashboard, organogram (view + export), departments, positions, employees, imports, audit-log, users, and settings, drives the real action with a mocked session for all 3 roles and asserts success/`/access-denied` matches `docs/AUTHORIZATION_MATRIX.md` §3 exactly, plus a cross-tier sweep confirming an unauthenticated caller gets `/sign-in` (never `/access-denied`) and a `DISABLED`-status user is blocked before the permission check even runs. Organogram search/filter/focus were not given a separate case — per §4, they're pure client-side computation over the same `organogram:view` payload, no separate server surface exists.
   - **"Cross-company isolation with overlapping codes"** (10 tests): two companies are built with the exact same codes (department `ENG`, position `POS-001`, employee `EMP-001`) plus colliding import-job filenames and export-job scope labels. For every module, confirms list/search scopes to the caller's own company only, a cross-company id in a get/update/archive/role-change/disable action resolves as not-found (never leaking or mutating the other company's same-coded record), and — for the audit log specifically — that HR_EDITOR's category restriction (`docs/AUTHORIZATION_MATRIX.md` §4's `USER_ADMINISTRATION` exclusion) holds even within the caller's own company.
2. `e2e/rbac-matrix.spec.ts` (new, 3 tests, one per role). Additive to the existing per-module specs (`e2e/imports.spec.ts`, `e2e/audit-log.spec.ts`, `e2e/settings.spec.ts`, `e2e/users.spec.ts`), which each already assert one hand-picked "this role is denied this one route" case. This file instead (a) asserts real, browser-rendered nav-item visibility for all 3 roles — the only prior automated check, `components/layout/app-shell.test.tsx`, mocks `hasPermission` at the component level rather than rendering with a real session, and `docs/NEGATIVE_SCENARIOS.md`'s A19 previously listed role-specific direct-URL denial as manual-only — and (b) walks all 3 roles × all 9 `config/navigation.ts` routes via direct `page.goto()` (never going through the nav), confirming every denied combination lands on `/access-denied` and every allowed one renders its own heading. The expected allow/deny matrix is derived from the app's own `roleHasPermission`/`NAV_ITEMS`, never a second hand-maintained copy.

## Performance Testing (Step 14)

Thresholds for every scenario were written into `docs/PERFORMANCE_REPORT.md` BEFORE any test was run, per this phase's non-negotiable rule. 18 organogram/dashboard-assembly scenarios (100/500/1,000 positions × wide/deep/mixed shapes) all passed comfortably. Three scenarios failed their pre-committed thresholds — none of the thresholds were loosened after the fact:

- **CSV import at 1,000/5,000 rows (DEF-009, High).** Originally failed outright (Prisma's default 5s transaction timeout aborted the whole import). Fixed the hard failure this phase (`withTransaction` now accepts optional `{timeout, maxWait}`; `executeImportJob` passes `{timeout: 120_000, maxWait: 10_000}`) — but this only converts the failure mode, it does not make import fast: a real post-fix measurement shows **31.8 seconds for 1,000 rows** (threshold was 10s) and **still incomplete after 300 seconds for 5,000 rows** (threshold was 30s). The root cause (fully sequential per-row processing, no batching) requires either bulk-write batching or an async job model to truly fix — both out of scope to implement silently during hardening. **Not fully resolved — requires a stakeholder decision** (see `docs/DEFECT_REGISTER.md` DEF-009).
- **PNG export at 500/1,000-node scale (DEF-010, Medium).** 3.6-18.3 seconds measured against a 2.5-6s budget. Not a correctness bug (every PNG produced was valid) — a real synchronous-latency concern. PDF export at the same scale stays within budget and remains a working alternative. **Not fixed — requires a stakeholder decision.**
- **Hierarchy-move concurrency (DEF-006, High).** Two individually-valid concurrent `movePosition` calls (A moved under B, B moved under A at the same instant) could jointly create a real, persisted reporting cycle — reproduced deterministically 4/4 times. **Fixed this phase**: added `lockPositionsForUpdate` (`lib/repositories/position.repository.ts`), a company-scoped `SELECT ... FOR UPDATE` on the moved position and its proposed new parent (ascending-id order, deadlock-safe), called at the very start of `movePosition`'s transaction, before the cycle-detection read. Re-verified 5/5 clean runs post-fix (2 showed the ideal `fulfilled=1/rejected=1` outcome with a genuine `CycleError`; 3 showed both callers safely refusing) — a cycle never formed in any run, before or after. No longer a release blocker.

Full detail, the pre-committed threshold table, and all real measurements: `docs/PERFORMANCE_REPORT.md`.
