# User Acceptance Testing (UAT) Plan — Dynamic Organogram Manager

## 1. Purpose and scope

This is the plan for User Acceptance Testing of the Dynamic Organogram Manager MVP (Phases 1–12), performed during Phase 13 ("Release Hardening"). It is written for a non-technical HR tester working alongside a technical facilitator who can run the seed script and, if needed, the CLI recovery tool.

UAT verifies that the application supports the real HR workflows described in `docs/PROJECT_SPEC.md` and `docs/HR_USER_GUIDE.md`, for each of the three real roles (VIEWER, HR_EDITOR, ADMIN — see `docs/AUTHORIZATION_MATRIX.md`), and that it correctly rejects the things it should reject (`docs/NEGATIVE_SCENARIOS.md`). It does not re-test what automated tests already cover exhaustively; it exercises the product the way a real HR user would, end to end, in a real browser.

**Out of scope**, per `docs/PROJECT_SPEC.md`'s MVP Exclusions and `CLAUDE.md`: drag-and-drop hierarchy editing, dotted-line/secondary reporting, historical/point-in-time organogram views, multi-step approval workflows, and any HRMS/external-system sync. Do not test for these — they are deliberately absent, not missing.

## 2. Environment and access

### 2.1 The UAT dataset

A dedicated, entirely fictional company — **"Brightloop Fictional Co."** (company code `UAT-DEMO`) — is seeded specifically for this testing pass via:

```
npm run db:seed:uat
```

This is separate from `prisma/seed.ts`'s "Northwind Example Co." dataset used for day-to-day development; both can coexist in the same database without conflict. The script is idempotent — running it again is always safe and never duplicates data — and refuses to run at all if `NODE_ENV=production` (see `prisma/seed-uat.ts`'s header comment for the full rationale).

The seeded company includes, so every scenario below has real data to exercise:

- 12 departments (including two nested under Engineering: Platform Engineering, Data Engineering)
- 38 positions spanning a wide leadership layer (9 positions reporting directly to the CEO) and a deep branch inside Engineering (7 organizational levels)
- A mix of Active, Planned, and Inactive positions, and Occupied and Vacant positions at multiple levels (including a vacant VP-level position and a vacant deepest-level position)
- 6 job grades, independent of organizational level
- 31 employees, including one with no current position assignment at all, one with a full assignment history (a past, ended assignment plus a current one, from a real transfer), and one who has been terminated (whose former position is now vacant)
- A real audit trail generated by actually performing the department/position/employee/assignment/transfer/termination/hierarchy-move actions through the same service layer the application itself uses — not fabricated rows
- Three demo user accounts, one per role (see §2.2)
- Ready-to-use example CSV files for all four import types, under `docs/uat-fixtures/`

### 2.2 Signing in as a tester

This application authenticates exclusively through **Company SSO** (no passwords exist anywhere in the system — see `docs/DECISIONS.md` P8). The seed script reserves three accounts:

| Email                 | Role      |
| --------------------- | --------- |
| `uat.admin@<domain>`  | ADMIN     |
| `uat.editor@<domain>` | HR_EDITOR |
| `uat.viewer@<domain>` | VIEWER    |

`<domain>` is whatever the environment's `AUTH_ALLOWED_EMAIL_DOMAINS` is configured to (the seed script reads it automatically; it falls back to `northwind-example.test` — this repository's existing local convention — only if that variable is unset).

**Before testing begins**, the facilitator must confirm with whoever administers the environment's actual Identity Provider that a real test-IdP account exists for each of these three exact email addresses — reserving the `User` row in this application's own database (which the seed script does) is necessary but not sufficient; the tester also needs a real account at the IdP itself to complete the SSO round-trip. If this environment has no live IdP configured yet (a real possibility — `docs/DECISIONS.md` P8 notes the specific SSO provider is still not finalized), coordinate with the facilitator on how sign-in will actually be demonstrated for this pass; do not treat "no IdP configured" as blocking every other scenario below, but do flag it rather than silently skip §2.2's own verification.

Once signed in, a tester switches roles simply by signing out and back in as a different one of the three seeded accounts.

### 2.3 Known issues to be aware of before testing

Two open, already-tracked defects can genuinely affect what a tester observes — see `docs/DEFECT_REGISTER.md` for full detail. They are not new bugs to report if encountered:

- **DEF-009**: uploading a very large CSV file (several hundred to a few thousand rows) can fail outright with a timeout-shaped error rather than a normal validation result. The example fixture files in §4 are small (2 rows each) and will not trigger this; only a deliberately large custom file would.
- **DEF-006**: two hierarchy moves submitted at almost the exact same instant by two different people can, in rare cases, both succeed even though together they'd form a cycle. Not expected to surface in a normal single-tester UAT pass.

## 6. Scenario Set 4 — Negative UAT scenarios

These confirm the application correctly **rejects** things it should reject. Representative examples pulled directly from `docs/NEGATIVE_SCENARIOS.md` (IDs shown so a facilitator can cross-reference the full automated-test evidence) — this is a sample for a human tester to spot-check, not the complete catalog.

| #   | Scenario (ref)                                       | Steps                                                                                                                                                            | Expected outcome                                                                                                                                      |
| --- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| N1  | Duplicate code, different case (DEP2/POS1/EMP1)      | As HR_EDITOR, try to create a department/position/employee whose code differs only in letter case from an existing one (e.g. `uat-eng` vs. `UAT-ENG`).           | Rejected with a clear "already in use" message — codes are compared without regard to case.                                                           |
| N2  | Self-reporting / reporting cycle (POS4/POS5/POS7)    | Try to set a position's Reports-To to itself, or move a manager beneath its own direct report.                                                                   | Rejected outright, with a clear message — never silently applied, never a corrupted chart.                                                            |
| N3  | Second root position (POS6)                          | Try to create a second position with no Reports-To (leave the field blank on a create, not just an edit).                                                        | Rejected, correctly naming the actual conflict (only one root position is allowed per company) rather than a misleading "duplicate code" message.     |
| N4  | Hidden-nav direct URL access (A19)                   | As VIEWER, type `/imports` directly into the address bar.                                                                                                        | Redirected to Access Denied — identical to clicking a link that was never shown.                                                                      |
| N5  | Unauthenticated access (A34)                         | Sign out completely, then navigate directly to `/dashboard`.                                                                                                     | Redirected to the sign-in page.                                                                                                                       |
| N6  | CSV file with a blocking error (CSV44)               | As HR_EDITOR, upload a Position CSV containing a deliberately duplicated `positionCode` within the same file.                                                    | Validation reports the error clearly against both rows; the Confirm/Execute controls remain blocked — nothing is committed.                           |
| N7  | CSV denylisted column (CSV29/CSV30)                  | Upload a Position CSV that includes an extra `organizationalLevel` column.                                                                                       | Rejected as a blocking file-level error before any row is even evaluated — organizational level can never be set via import.                          |
| N8  | Assigning an already-assigned employee (EMP12/EMP13) | Try to assign an employee who already holds an active position to a second position, without first transferring or ending the first assignment.                  | Rejected with a clear conflict message.                                                                                                               |
| N9  | Reassigning a terminated employee (EMP19)            | On the employee terminated in B8, confirm no "Assign to Position" control is offered at all.                                                                     | The control is absent entirely for a terminated employee — there is no path to attempt this from the UI.                                              |
| N10 | Last-ADMIN protection (AUD27/AUD28)                  | As ADMIN, with only one active ADMIN in the company, try to disable or demote yourself.                                                                          | Rejected with a message that the company must always have at least one active ADMIN.                                                                  |
| N11 | HR_EDITOR reaching an ADMIN-only category (AUD15)    | As HR_EDITOR, filter the Audit Log to "COMPANY_SETTINGS".                                                                                                        | Zero results, never an error revealing the category exists.                                                                                           |
| N12 | Stale settings write (AUD46/AUD47)                   | Same as Scenario A13 above.                                                                                                                                      | Rejected with "This record was changed by someone else."                                                                                              |
| N13 | Invalid form input                                   | As HR_EDITOR, try to create a department with a name that is only spaces, or a position with a 200-character title, or an employee with an invalid email format. | Each is rejected client-side with an inline validation message before any request is even sent — and would be independently rejected server-side too. |
| N14 | Import mode CREATE_ONLY conflict (CSV41)             | Re-upload `docs/uat-fixtures/department-import-example.csv` a second time, but choose mode "Create only" instead of UPSERT.                                      | Rejected — the row's code already exists, and CREATE_ONLY never silently updates or skips it.                                                         |

## 7. Reporting issues found

For anything that doesn't match its expected outcome above, note: the scenario ID, the exact steps taken, what you expected, and what actually happened (with a screenshot if visual). Check `docs/DEFECT_REGISTER.md` first — the issue may already be a known, tracked item (see §2.3) rather than something new to log.

## 8. Sign-off criteria

UAT for this pass is considered complete when every scenario in Sections 3–6 has been executed at least once with a recorded outcome, and every discrepancy from an expected outcome has either been triaged into `docs/DEFECT_REGISTER.md` or explicitly accepted by name by whoever owns the release decision — consistent with `docs/PROJECT_SPEC.md` §15's MVP acceptance criteria and the `phase-quality-gate` skill's verification standard.
